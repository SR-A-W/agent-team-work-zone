# `/quickstart` — 一条命令组建第一支团队

/quickstart 是傻瓜版、增强版的 /onboard：/onboard 会向用户提问，所以这里不直接调用它，而是读 /onboard 的快速模式一节，替用户填好所有答案，再接着把团队建好。

你是用户当前这个 Claude Code 会话，接下来要成为这个项目的团队负责人（lead）。按下面的步骤，一次跑完：看项目 → 判断订阅档位 → 定阵容 → 建 lead 工位 → 派生成员 → 等成员就绪 → 判断显示方式 → 判断登录方式 → 发结束消息。

**做什么**：
- 检查环境、看项目、定阵容；
- 建 lead 工位、派生成员、等所有成员就绪；
- 最后发一条结束消息：团队有谁、怎么用，并提议一个 20 分钟内能做完的小任务。

**不做什么**：
- 不自动开始任何任务。成员启动后只发就绪回执，然后等待。
- 不覆盖已有的工位或团队；只接着做自己没跑完的那一次。
- 不改全局设置（`~/.claude/settings.json`）。
- 不向用户提任何问题。遇到前提不满足，说明情况和改法后停下。

## 总规则：用户能看到的文字

整个运行过程中，用户能看到的文字只有两处：
1. 系统提示**明确显示**不是自动权限模式时，开头的一句提示（见 Step F）；
2. 最后的结束消息（见 Step F）。

等回执的中间回合**什么都不输出**，一个字也不输出。

自检不通过而停下时，输出的是**停止消息**：只有（按 Step F 的条件出现的）开头两行，加上 Step A 里给出的那段停止说明；**不带**"## 团队已经组建好了"或结束消息的任何其他一节，也不加别的句子。除此之外不出文字、不提问题。**结束消息发出之后**，本次运行里任何不是用户发起的唤醒（迟到的回执、成员的空闲通知、漏停的计时）都只做必要的记录，不输出文字；用户发来的消息照常回答。

## 本技能用到的说法

- **工作区**：项目根目录下的 `_agent_team_work_zone/` 目录。
- **lead 工位**：`_agent_team_work_zone/<slug>_team/`，就是你（lead）的目录。
- **slug**：lead 工位名去掉 `_team` 后剩下的那一段，只含小写字母和数字。成员名一律是 `<slug>-<角色>`。
- **登记表**：lead 工位里的 `TEAMMATE_INFO.json`。
- **回执**：成员启动后用 SendMessage 发给你的那一行 `Ready. Model: …, ID: …`。
- **快速模式**：/onboard 和 /spawn-team 里各有一节"快速模式（只由 /quickstart 使用）"：跳过逐项向用户确认，直接用本技能传过去的答案。
- **未完成标记**：lead 工位里的 `.quickstart_incomplete` 文件。建好 lead 工位目录后第一个写它，结束消息发出前删除。它在，就说明那一次 /quickstart 没跑完。

## 运行顺序

```
用户输入 /quickstart [任务描述]
  A  自检（先第 1 项，再第 0 项，再第 2–6 项）
     · 第 0 项命中 → 读出上次的答案，按"续做"处理
     · 系统提示明确显示不是自动模式 → 先给一句提示，继续
     · 其他前提不满足 → 说明情况和改法，停下
  B  看项目、推断类型
  C  整理任务描述
  C2 判断订阅档位 → 定成员模型、人数上限、给 lead 的建议
  D  定阵容
  E1 按 /onboard 的快速模式建 lead 工位 → 建好目录后第一个写未完成标记 → 写 model_policy.json
  E2 按快速模式调用 /spawn-team → 建成员工位、写登记表、写阵容记录、派生成员
  E3 收回执，到截止时间为止（首次派生 + 600 秒）
  E4 判断显示方式：同进程还是分窗格
  E5 判断登录方式：是不是 claude.ai 账号
  F  停掉未完成的计时 → 删除未完成标记 → 发结束消息
```

## Step A: 自检（不问用户）

**执行顺序：先做第 1 项**（只看系统提示，不调用任何工具），**再做第 0 项，然后第 2–6 项。** 第 0 项和其后各项都要运行命令；先跑它们的话，非自动模式下确认框会在提示出现之前就弹出。

以下"当前目录"指 Claude Code 启动的目录（Bash 里 `pwd` 的结果）。

**第 1 项：权限模式是不是自动模式**
- **只看**你自己的系统提示里有没有说明当前权限模式（例如"自动模式已开启"一类的话）。**不读任何设置文件**：较新的 Claude Code 里，自动模式是交互终端会话的内建起始模式，设置文件里没写 `defaultMode` 的用户多数其实就是自动模式，按文件判断会误报。
- 系统提示**明确显示**不是自动模式 → 立刻输出 Step F 的"开头的提示"，然后继续。记下"非自动模式"。
- 系统提示明确显示是自动模式 → 记下"自动模式"，什么都不说。
- 看不出 → 记下"看不出"，什么都不说。

**第 0 项：有没有没跑完的 /quickstart**
- 看 `_agent_team_work_zone/*_team/.quickstart_incomplete` 是否存在（`ls -d _agent_team_work_zone/*_team/.quickstart_incomplete 2>/dev/null`）。
- 有一个 → 按本节末尾的"续做"处理，不管那个目录里还缺什么，第 5 项跳过。
- 有两个或更多 → 停下，列出这些目录，请用户删掉不要的那个目录后再输入 /quickstart。
- 没有 → 继续。（当前目录下没有 `_agent_team_work_zone/` 时，这一项自然查不到，交给第 2 项。）

**第 2 项：是否在装了工作区的项目根目录启动**
- 判断：当前目录下有 `_agent_team_work_zone/README.md`。
- 原因：在子目录启动时，技能和根目录的 CLAUDE.md 会从上级目录找到，所以 /quickstart 照样能运行；但 `.claude/settings.json` 只从启动目录读，里面的团队功能开关和 hooks 都不生效。所以必须在这里抓住这种情况。
- 不满足 → **停下**，按下面的顺序找，给出对应的说明：
  1. 往上逐级找父目录，有 `_agent_team_work_zone/README.md` 的 → "你在项目的子目录里启动了 Claude Code。这样技能能用，但团队功能和自动保存的提示都不会生效。请退出，进入 `<父目录>` 再启动 Claude Code，然后输入 /quickstart。"
  2. 往下两层找（`find . -maxdepth 3 -path '*/_agent_team_work_zone/README.md'`），找到的 → "工作区装在 `<子目录>` 里。请退出，进入 `<子目录>` 再启动 Claude Code，然后输入 /quickstart。"
  3. 都没有 → "这个目录还没有安装 agent-team-work-zone。在项目目录下运行 `npx agent-team-work-zone init --lang zh`（需要 Node.js 18+），然后在同一个目录启动 Claude Code，输入 /quickstart。"

**第 3 项：团队功能在当前会话是否生效**

以信号 (1) 为准；(2)、(3) 只在 (1) 判不出（例如读不到自己的工具说明）时才用，不用来推翻 (1)。

- (1) **首要信号：你自己的 Agent 工具参数里有没有 `name`。** 不调用任何工具，读你自己的工具说明即可。团队功能开着时，Agent 工具的参数里有 `name`（通常还有 `team_name`、`mode`）；关着时没有这几个。有 `name` → 生效；没有 → 未生效。
- (2) 本会话自己的团队目录：分两步：先在 Bash 里运行 `echo "$CLAUDE_CODE_SESSION_ID" | cut -c1-8` 取会话编号前 8 位，再运行 `test -f ~/.claude/teams/session-<前 8 位>/config.json && echo yes`（`<前 8 位>` 换成上一步的结果）。输出 yes → 生效。只能看本会话自己的这个目录，**不能**看"有没有任何团队目录"（正常 /exit 会删除该目录，没有正常退出的会话会留下它）。
- (3) 快速的"没开"信号：Bash 里 `printenv CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` 没有输出（这个变量没设置；以 1 退出不算命令失败）→ 未生效。为 `1` 不能说明开着（可能来自用户的 shell 配置文件）。
- **不要用**这些来判断：ListAgents 的输出、工具清单里有没有 SendMessage 或 ListAgents（两种状态下相同）、Agent 调用是否立即返回、`.claude/settings.json` 里有没有写开关（子目录启动时文件里有、会话却没读）。
- 判定未生效 → **停下**，先看**当前目录**（第 2 项已确认它就是项目根目录）下的 `.claude/settings.json` 里有没有 `"CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"`：
  - (i) 没有 → 补上：先备份（`cp -p .claude/settings.json .claude/settings.json.bak`，文件不存在就跳过备份），再用和安装脚本相同的合并写法：
    ```bash
    f=.claude/settings.json; [ -f "$f" ] || echo '{}' > "$f"
    tmp="$(mktemp "$(dirname "$f")/.settings.XXXXXX")" \
      && jq '.env = (.env // {}) | .env.CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS = "1"' "$f" > "$tmp" \
      && jq empty "$tmp" && cat "$tmp" > "$f"; rm -f "$tmp"
    ```
    没有 jq 就不改文件，只告诉用户要在 `.claude/settings.json` 里加上 `{ "env": { "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1" } }`。然后说："团队功能在这个会话里没有打开。我已在 `.claude/settings.json` 里加上了开关（或：请在 `.claude/settings.json` 里加上……）。请退出 Claude Code，在这个目录重新启动，再输入 /quickstart。"
  - (ii) 有 → "团队功能在这个会话里没有打开。请退出 Claude Code，在项目根目录 `<当前目录>` 重新启动，再输入 /quickstart。"
  - 两种都再加一句："第一次在这个目录启动时会问是否信任这个文件夹，要选 "Yes, I trust this folder"（默认高亮的是 "No, exit"，选它会直接退出）。"

**第 4 项：工作区技能是否装好**
- 判断：`.claude/skills/onboard/SKILL.md` 和 `.claude/skills/spawn-team/SKILL.md` 都在。
- 不满足 → **停下**："团队技能没有装全。请在项目根目录运行 `bash _agent_team_work_zone/resources/scripts/bootstrap.sh` 重新安装，然后退出 Claude Code、在这个目录重新启动，再输入 /quickstart。"

**第 5 项：是否已有团队或工位**（第 0 项命中时跳过）
- 所有以 `.` 开头的目录一律忽略（安装会带 `.upgrade/`，hook 会生成 `.hook_logs/`）。
- 只认两种：
  1. 团队：`_agent_team_work_zone/*_team/TEAMMATE_INFO.json`；
  2. 扁平工位：`_agent_team_work_zone/` 下不以 `.` 开头、带 `README.md`、且不是 `meeting_room/`、`archive/`、`resources/`、`docs/` 的目录。
- 有团队 → **停下**："这里已经有团队 `<目录名>`。电脑或 Claude Code 重启后要把成员唤回来，输入 /reactivate-team；要再加一个角色，用 /onboard。"
- 只有扁平工位 → **停下**："这里已经有工位 `<目录名>`。请在它原来的对话里继续，或用 /onboard 新建。"

**第 6 项：是不是 git 仓库，仓库根是不是项目根**
- 判断：`git rev-parse --show-toplevel` 成功，且结果等于当前目录。
- 不是 git 仓库 → 继续；记下"不是 git 仓库"，结束消息里提一句好处。
- 仓库根在更外层 → 继续；Step B 里所有 git 依据一律当弱信号。

**检查命令本身出错时**（例如没有 jq、git 报错）：不当作"不满足"；记下"未能检查：<哪一项、为什么>"，继续，结束消息里说一句。

### 续做（第 0 项命中时）

- 从未完成标记里读出上次的项目简介、项目类型、阵容、任务描述，**不重新推断**（Step B、C、D 跳过）。订阅档位读 lead 工位里的 `model_policy.json`；没有这个文件 → 照 Step C2 重新判断，在 E2 之前写入。第 1–4 项照常检查；第 5 项跳过；第 6 项只用于结束消息。
- 按目录里**已有**的东西决定从哪一步接着做，只补缺的，不重写已有的：
  1. 缺 lead 工位的文件（README、登记表等）→ 从 E1 接着做（/onboard 快速模式只补缺的文件）。
  2. 登记表里没有成员 → 从 E2 开始。
  3. 登记表里有成员 → **逐个处理，不一律重派**：
     - 本会话里已经收到过它的回执 → 算就绪；
     - 否则按 E3 发一次探测：返回"不可寻址"（`No agent named … is currently addressable`）→ 重派；发送成功 → 当作"还在"，进入等回执；
     - 登记了、但工位或阵容记录里的派生提示缺失的 → 先补齐，再派生。
  4. 进入 E3 时**重新计截止时间**（现在 + 600 秒），不沿用上一次的。
- 为什么要逐个探测：同一个会话里续做时（例如用户在派生途中按了 Esc，又输入 /quickstart），之前派出的成员还活着。一律重派会得到带后缀的副本，又会把活着的原件当成坏的移走。重启后续做时，所有成员都已下线，探测会全部返回"不可寻址"，结果和一律重派相同。

## Step B: 看项目、推断类型

**输入**：
- 项目文件清单。排除 `.git/`、`_agent_team_work_zone/`、`.claude/`、`node_modules/`、`.venv/`、`venv/`、`__pycache__/`、`dist/`、`build/`、`.ipynb_checkpoints/`，以及所有以 `.` 开头的目录。文件数超过 5000 时只看前两层。
- 顶层 README 全文（有的话；超过 200 行只读前 200 行）。
- 顶层代码清单文件里的名称和描述字段（有就读）：例如 `package.json` 的 `name`、`description`，`pyproject.toml` 的 `name`、`description`，`Cargo.toml` 的 `name`、`description`。
- 顶层目录往下两层的结构。
- git 可用时（第 6 项判为 git 仓库）：提交数（`git log --format=%H | wc -l`）、作者数和提交最多的作者（`git log --format=%an | sort | uniq -c | sort -rn | head -3`）、最近一次提交日期（`git log -1 --format=%cs`）、`origin` 的地址（`git remote -v`；地址里若带用户名或令牌，只用主机名和仓库路径）。只用 git log、git remote、git config、git rev-parse 这几条只读命令，不读任何凭据。
- 任务描述。

**项目类型**：从上往下，先命中的为准。"强"表示信号明确；"弱"表示信号不足，阵容按 Step D 的"信号弱时"定。

| 顺序 | 条件 | 结论 | 强/弱 |
|---|---|---|---|
| 1 | 排除后文件数 ≤ 3，且都是 README、LICENSE、`.gitignore`、`CLAUDE.md` 这类 | 空项目 | 强 |
| 2 | 顶层有代码清单文件：`package.json`、`pyproject.toml`、`setup.py`、`setup.cfg`、`Cargo.toml`、`go.mod`、`CMakeLists.txt`、`pom.xml`、`build.gradle`（`requirements.txt`、`Makefile` 不单独算） | 代码库 | 强 |
| 3 | 顶层或第二层有 `.tex` 文件含 `\documentclass`，没有命中第 2 条，且代码文件 < 20 个 | 论文或写作 | 强 |
| 4 | 有代码文件（`.py .js .ts .go .rs .java .c .cpp .h .sh .rb .jl .m .r` 等）≥ 1 个，且 `.ipynb` 加数据文件（`.csv .tsv .parquet .jsonl .h5 .npy .pkl`）的数量超过代码文件 | 数据或实验 | 弱 |
| 5 | 有代码文件 ≥ 1 个（含只有 `README.md` + `main.py` 的新项目） | 代码库 | 弱 |
| 6 | 有 `.ipynb` 或数据文件，没有其他代码 | 数据或实验 | 弱 |
| 7 | 只剩 `.md .txt .rst .pdf .docx` 这类 | 只有文档 | 弱 |

**代码库再分两种：自己的仓库继续开发，还是复现或使用别人的仓库。** 只在项目类型是代码库时判断，从上往下，先命中的为准：

| 顺序 | 条件 | 结论 | 强/弱 |
|---|---|---|---|
| 1 | 任务描述里按**整词**出现"复现、reproduce、replicate、跑一下这个仓库、试用"这类词（"跑通测试""runtime""retry"这类不算） | 别人的 | 强 |
| 2 | 任务描述里按整词出现"继续开发、加功能、修 bug、重构、我的项目、my project" | 自己的 | 强 |
| 3 | 本机 `git config user.email` **已设置**，且 `git log --author="<<邮箱>>" --fixed-strings --format=%H` 输出的行数大于 0（行数就是写进依据的提交次数；邮箱两侧带尖括号，只匹配作者栏里的完整邮箱）。邮箱没设置时跳过本条：空的 `--author=` 会匹配所有提交 | 自己的 | 强 |
| 4 | 装了 gh 且已登录；远端主机是 `github.com`；远端拥有者与 `gh api user --jq .login` 完全相同（不分大小写）；且不是分叉（`gh repo view --json isFork`） | 自己的 | 强 |
| 5 | 第 4 条的前提都满足，但拥有者不同；第 3 条为零提交；邮箱已设置 | 别人的 | 弱 |
| 6 | 远端怎么取：先取 `origin`；没有 `origin` 但恰好只有一个远端，就取它；多个远端且没有 `origin`，或主机不是 `github.com` → 第 4、5 条不适用 | — | — |
| 7 | 以上都没有结论 | 看不出是谁的：阵容按"自己的"处理，结束消息用"看不出是谁的"那句意图句 | 弱 |

第 6 项判出"仓库根在更外层"时，第 3、4、5 条的结论一律当弱。

**输出**：
- **项目简介**：一到三句话，写这是什么项目、用什么语言或工具写的、主要部分有哪些、谁写的或多大规模（例如"一个用 PyTorch 写的文本生成实验仓库，主要是训练脚本和几个模型配置；27 次提交，作者两人，最近一次提交在今年 8 月"）。只写从文件里读到的事实，读不到就少写，不编。空项目不写简介。
- 项目类型和强弱；
- 代码库时：自己的还是别人的，以及强弱；
- 每条结论所依据的一两条事实（例如"顶层有 `pyproject.toml`""本机邮箱在这个仓库有 3 次提交"）。

这些都写进未完成标记和阵容记录（续做时直接用）。

**失败时**：git 命令出错 → 跳过对应依据；判断不了 → 按弱处理。

**整体信号强弱**：项目类型为"弱"，或代码库的"自己的还是别人的"为"弱" → 整体为"信号弱"；否则为"信号明确"。

## Step C: 任务描述

- **有**（`$ARGUMENTS` 非空）：原样作为团队目标；用来定规模（Step D）、提议小任务（Step F）。
- **没有**：不编造目标；阵容按 Step D 的"没有任务描述"组建。
- **任务和项目对不上**（例如空目录里说"复现"）：照用户的话组建，结束消息里如实说缺什么。

## Step C2: 判断订阅档位

**为什么**：成员用什么模型、能有几个人，按用户的订阅来定，免得一上来就把额度用光。本技能不问用户，一律用默认值；用户以后说一句就能改。成员的思考强度跟着你（lead）这个会话，派生时没法单独设，所以思考强度只能作为对你的建议。

**怎么做**：
1. 先从你自己的系统提示里读出你（lead）当前的模型（例如"You are powered by the model named …"或模型 ID），然后在 Bash 里运行 `bash _agent_team_work_zone/resources/scripts/atwz_detect_tier.sh --model "<当前模型>"`（读不到模型就不加 `--model`）。它输出一行 JSON，取 `tier`、`source`、`lead_effort_current`（lead 当前的思考强度，脚本按环境变量、项目设置、用户设置、模型默认依次读出）和 `lead_advice`（脚本拼好的给 lead 的建议句，可能为空）。脚本出错、没有输出或解析不出 → `tier` 按 `unknown`，`lead_advice` 按空。
2. 按下表取值，记为"策略"：

| `tier` | 档位名 | 成员模型 | 成员人数上限 | 给 lead 的模型建议 | 给 lead 的思考强度建议 |
|---|---|---|---|---|---|
| `pro` | Pro | `haiku` | 2 | `sonnet` | `medium` |
| `max_5x` | Max 5x | `sonnet` | 4 | `opus` | `medium` |
| `max_20x` | Max 20x | `opus` | 5 | `opus` | `high` |
| `team` | Team / Enterprise | `sonnet` | 4 | `opus` | `medium` |
| `api` | — | `sonnet` | 5 | 不建议 | 不建议 |
| `unknown` | — | `sonnet` | 5 | 不建议 | 不建议 |

3. 建好 lead 工位后（Step E1 之后、E2 之前），把策略写进 `<lead 工位>/model_policy.json`（字段见 `docs/model_policy_schema.md`），用带校验的写法（任一步失败都删掉临时文件、不留半个文件）：
   ```bash
   policy=_agent_team_work_zone/<slug>_team/model_policy.json
   ts="$(date -u +%Y-%m-%dT%H:%M:%SZ)"
   tmp="$(mktemp "$(dirname "$policy")/.policy.XXXXXX")" \
     && jq -n --arg tier "<tier>" --arg src "<source>" --arg mm "<成员模型>" --argjson max <人数上限> \
          --argjson lm '<"sonnet" 或 "opus" 或 null>' --argjson le '<"medium" 或 "high" 或 null>' --arg ts "$ts" '
        {schema_version: 1, tier: $tier, tier_source: $src, choice: "default",
         member_model: $mm, max_members: $max,
         lead_model_suggested: $lm, lead_effort_suggested: $le,
         decided_by: "quickstart (automatic)", detected_at: $ts, updated_at: $ts}' > "$tmp" \
     && jq empty "$tmp" && mv "$tmp" "$policy" && chmod 644 "$policy" || rm -f "$tmp"
   ```
   续做时：文件已在 → 直接读它，不重新判断、不重写；文件不在 → 照本步重新判断并写入。写入失败 → 不影响团队，照策略继续，结束消息里按"有未能检查的项"说一句。
4. 记下 `lead_advice`，原样用在结束消息里；不要改写，也不要自己另拼。

`source` 只含字段名和取值；不要把 `claude auth status` 的原始输出写进任何文件或消息。

**给 lead 的建议**：就是脚本输出的 `lead_advice`（规则见 `docs/model_policy_schema.md` 的"给 lead 的建议怎么写"一节，由脚本实现）；为空就不写。

## Step D: 定阵容

**共同原则**：
- 至少两人，最多按策略的成员人数上限（Pro 时就是固定 2 人）。
- 成员模型一律用策略里的值（Step C2）；永远不用 `fable`。派生时不传思考强度（对成员不起作用，成员跟着 lead）。
- 计划模式审批一律关闭（`plan_mode_gating: false`）。
- 范围：`planner` 和 `reviewer` 只读项目文件，只写本团队的 `roundtable/`；动手的人可以改项目文件。所有人都不碰 `_agent_team_work_zone/` 下别人的工位、`.claude/`、`.git/`。
- 成员名 `<slug>-<角色>`，角色词从这几个里选：`coder`、`planner`、`setup`、`writer`、`reviewer`、`runner`、`reporter`。
- 同一角色两人时，写 `coder` 和 `coderb`。不用连字符加数字，免得和系统自动加的后缀混淆。

**信号明确时**，按项目类型：

| 项目类型 | 动手的人 | 规划的人 | 有任务时按需要依次加 |
|---|---|---|---|
| 空项目 | `coder`（inline，编码） | `planner`（inline） | `setup`（原型 `resources/role_archetypes/infra/env-configurator.md`）、`reviewer`（通用子代理 `reviewer`） |
| 代码库·自己的 | `coder`（inline，写明项目语言和测试命令） | `planner` | `reviewer`、`coderb`、`setup` |
| 代码库·别人的 | `setup`（原型 `resources/role_archetypes/infra/env-configurator.md`） | `planner`（读 README、列复现步骤和要对上的数字） | `runner`（原型 `resources/role_archetypes/coding/bash-scripter.md`）、`reporter`（原型 `resources/role_archetypes/analysis/result-reporter.md`） |
| 论文或写作 | `writer`（inline） | `planner`（理结构、查前后一致） | `reviewer`（inline，按投稿标准挑问题）、`reporter`（图表） |

**信号弱时**：`planner` + 动手一人（项目里有代码清单文件或至少 1 个代码文件 → `coder`，否则 → `writer`）；任务大时依次加 `reviewer`、`setup`。

**规模**：
1. 没有任务描述 → 两人：动手一人 + `planner`。动手的人：信号明确时按类型表（空项目和代码库是 `coder`，论文或写作是 `writer`）；信号弱时有代码就是 `coder`，否则是 `writer`。
2. 有任务描述 → 两人起；任务里每多一类明确的工作，按"依次加"一栏加一人。
3. 目标大（任务描述里按整词出现"写完、做完、整个、全部、完整、端到端、从零"这类词，或列出三件以上的事）→ 至少 4 人；人数上限小于 4 时取上限。
4. 无论如何不超过策略的成员人数上限。

**每个成员写清**：成员名、角色一句话、角色来源（inline / 原型路径 / 通用子代理名）、模型（策略里的值）、范围、禁区、交付物（"暂无，等 lead 派活"）。

**原型文件不存在时**：改用 inline 角色，阵容记录里注明。

**inline 角色的一句话写法**（写进派生提示的"角色定义"）：
- `coder`：在本项目里写代码、跑测试；写明项目语言和测试命令（看得出的话）。
- `planner`：读项目、理清结构，产出计划和项目地图；只读项目文件，只写本团队 `roundtable/`。
- `writer`：写和改论文或文档。
- `reviewer`：只读，按要求挑问题，产出评审意见。
- `runner`、`reporter`、`setup`：按原型文件；没有原型时，一句话写明它负责的那一类工作。

## Step E1: lead 工位（按 /onboard 的快速模式）

**slug 规则**：
1. 把项目目录名按词拆开：非字母数字字符（`-`、`_`、`.`、空格等）算分隔；小写字母后面紧跟大写字母处也算分隔。
2. 每个词转小写，只保留 `a-z`、`0-9`，再按原顺序拼起来。
3. 以数字开头的，前面加 `p`（`2024exp` → `p2024exp`）。先加前缀，再看长度。
4. 总长 ≤ 16：照用。超过 16：从末尾整词去掉，直到 ≤ 16；第一个词（含前缀）本身就超过 16 时，截到 16 个字符。
5. 结果为空（例如目录名全是中文）→ 用 `proj`。

例：`codebase-others` → `codebaseothers`；`My-Project_v2` → `myprojectv2`；`deep-learning-experiments-2024` → `deeplearning`。

**名字**：
- 目录：`_agent_team_work_zone/<slug>_team/`（直接用 slug，不按 /onboard Step 2 的"转小写下划线"规则去转 `<Slug> Lead`）。
- `lead_name` 和成员表里的英文名：`<Slug> Lead`（slug 首字母大写）；中文名："项目主管"。
- 一句话职责：有任务描述时 "带领团队完成：<任务描述>"；没有时 "带领团队推进本项目"。

**执行**：读 `.claude/skills/onboard/SKILL.md`，找到"## 快速模式（只由 /quickstart 使用）"一节，照它执行，把上面的名字和下面的未完成标记内容交给它。/onboard 只允许用户直接调用，所以不要用技能工具调用它，而是读文件照做。/onboard 做完后，按 Step C2 第 3 条写 `model_policy.json`。

**未完成标记的内容**（纯文本，建好目录后**第一个**写）：

```
quickstart started: <ISO 8601 UTC 时间>
slug: <slug>
task: <任务描述，或 none>
summary: <项目简介，或 none>
project type: <类型>（<强/弱>）；依据：<一两条事实>
ownership: <自己的/别人的/不适用>（<强/弱>）；依据：<事实>
signal: <明确/弱>
lineup:
- <slug>-<角色> | 来源：<inline / 原型路径 / 子代理名> | 模型：<策略的成员模型> | <角色一句话>
- …
checks: <自动模式/非自动模式/看不出>；<是/不是 git 仓库>；<未能检查的项，或 none>
```

它只在 Step F 的结束消息发出前删除。

**失败时**：/onboard 快速模式报告"同名目录已存在且没有未完成标记" → 停下，结束消息说明这个目录已被占用、没有覆盖，请用户换个目录名或删掉它。

## Step E2: 成员工位与派生（按快速模式调用 /spawn-team）

用技能工具调用 `spawn-team`，参数以 `--quick` 开头，后面按下面的固定格式给出答案：

```
--quick
team: <slug>_team
project_root: <当前目录的绝对路径>
goal: <任务描述，或 none>
basis: <项目简介；项目类型、强弱、依据，按未完成标记里的写法>
lineup:
- name: <slug>-<角色> | source: <inline | archetype:<原型路径> | subagent:<子代理名>> | model: <策略的成员模型> | role: <角色一句话> | scope: <范围> | forbidden: <禁区>
- …
```

/spawn-team 照它的快速模式完成：派生提示、成员工位骨架、登记表、阵容记录（含"/quickstart 推断依据"一节）、并行派生所有成员。每个成员派生提示里的"当前任务"写："暂无。发完就绪回执后等待 lead 派活，不要自己开始任何工作。"

**记下首次派生时间**：在发出第一个 Agent 调用之前，运行 `date -u +%s`，记为 T0。截止时间 = T0 + 600 秒（续做时见上文）。

/spawn-team 派生完成后回到本技能的 E3，它自己的等待和确认清单都不执行。

**失败时**：
- 工位或登记表写入失败 → 不派生，结束消息报告失败的那一步。
- Agent 工具报错（例如 tmux 相关）→ 按 /spawn-team"终端 / tmux 相关"一节的说明判断原因，写进结束消息。
- 两种情况都保留未完成标记，用户修好后再输入 /quickstart 就会接着做。

## Step E3: 等回执与安全重派

**为什么这里可以自动重派**：/reactivate-team 不自动重派，是怕原来那个其实还活着，再派一个同名的就成了两份。这里有两道保护：只在原来那个探测为"不可寻址"时才重派；万一出现两份，立刻关掉多出来的那个。

**你会被这些唤醒**：成员的 SendMessage（回执或别的消息）、后台 `sleep` 结束、成员进入空闲时的通知。计时只用来在没人回执时定期检查。

**截止时间**：一个固定值 = T0 + 600 秒；重派不延长。

**计时**：用 Bash 的后台运行（`run_in_background`）执行 `sleep <秒数>`，秒数 = `min(180, 截止时间 − 现在)`；记下这个后台任务的编号。剩余时间 ≤ 0 时不再开新的计时。

**中间回合**：每回合只做处理，**什么都不输出**，一个字也不输出。用户在等待期间发来消息 → 先回答用户，回执处理照常继续。

**每收到一个回执**：
1. **发件人不在登记表里的，忽略**（带后缀的副本会用原件的路径完成启动，再用后缀名发回执）。
2. 核对模型：把 ID 写进该成员条目的 `model_resolved`（用 /spawn-team 6c 的带校验 jq 写入，加 `| .model_resolved = $mid`）。ID 不含策略的成员模型名（例如 `haiku`、`sonnet`、`opus`）→ 记下，留给结束消息。`Model: not stated` → 不写该字段，记下"没有报告模型"。
3. 回执带 `Unread: <文件>` → 用 SendMessage 让它把文件读完并确认。这件事不告诉用户。
4. 回执提到守则备份 → 记下备份位置，留给结束消息。
5. 所有登记的成员都到齐 → 进入 Step F。

**每次计时结束（一轮检查）**：对**每个**还没回执的登记成员发探测，不管 `.started` 在不在：
1. 用 SendMessage 发："这是一条启动检查。若你已启动，照常发就绪回执即可。"
   - 返回"不可寻址"（`No agent named … is currently addressable`）→ 它已经不在了 → 用同一个名字、同一份派生提示（阵容记录里有）**重派**。
   - 发送成功 → 这只说明消息进了它的收件箱，**不说明它还活着** → 继续等。
2. 已知限制：卡住或已崩溃、但名字还在的成员，每次探测都会"发送成功"，不会被重派，到截止时间才算失败。
3. 每个成员最多重派 2 次，都在同一个截止时间内。
4. 还没到截止时间 → 开下一次计时。

**重派回来的名字带了后缀**（例如请求 `myproj-coder`，返回的名字是 `myproj-coder-2`）：
1. 立刻给带后缀的副本发关闭请求：SendMessage 的 message 用 `{"type": "shutdown_request", "reason": "你是多派的，请不要写任何文件，直接同意关闭。"}`。这个请求要等副本的回合结束才送达；在那之前它多半已经用原件的路径跑完了启动步骤并用后缀名发来回执——这些写入内容相同、无害，它的回执按上面的规则忽略。
2. 换一个新的角色名：在原角色词后加字母，`coder` → `coderb` → `coderc`，跳过已被占用的。
3. **先**建新名的工位骨架（/spawn-team 6b）、在登记表里加新名的条目（6c 的带校验写入），**再**用新名派生。派生提示里的所有路径和名字都用新名。
4. 原名的登记项移到 `offboarded_teammates`，注明"启动失败，已由 <新名> 替代"；原名的工位目录原样留着。
5. 在阵容记录末尾补一句。
6. 新名的这次派生，算作这个角色的一次重派。
7. 截止时副本还没同意关闭 → 记下，结束消息里列出它。

**到截止时间还没回执的成员**：
- 登记表里把它的 `status` 记为 `failed_to_reactivate`（用 6c 的带校验写入）。
- 看它的 `.started`（`<lead 工位>/teammates/<名字>/.started`），与 T0 比较修改时间（`stat -c %Y`）：有且晚于 T0 → "它启动过，后来中断了"；没有 → "它没能启动，可能停在确认界面上"。
- 分窗格显示时，按 /spawn-team 6e 里的尽力而为办法读它的窗格；看到停在确认界面，就在结束消息里请用户去点确认。

**所有人到齐，或到了截止时间** → 先做 Step E4、Step E5，再做 Step E5 后面的"结束前"。

## Step E4: 判断显示方式：同进程还是分窗格

**为什么**：同进程显示（较新 Claude Code 的默认）时，成员都在你这个窗口里，没有各自的会话，只有你能接入远程控制；分窗格显示（tmux 或 iTerm2）时，每个成员有自己的窗格。结束消息里"怎么直接和成员说话"一句和远程控制一段，都按这里的结果写。

**什么时候做**：所有成员就绪或到了截止时间之后、发结束消息之前（这时成员已经派生，第 1 个办法才有东西可读）。

**按顺序判断，前一步得出结论就不看后一步**：
1. **读本会话团队文件里成员的显示方式**（要在首次派生之后读）：用 Bash `echo "$CLAUDE_CODE_SESSION_ID"` 取会话编号，用 Read 工具读 `~/.claude/teams/session-<会话编号前 8 位>/config.json`。**只看非 lead 的成员条目**——lead 自己的条目在分窗格时也是 `"tmuxPaneId": "leader"`、`"backendType": "in-process"`，不能拿来判断。
   - 成员的 `backendType` 全为 `"in-process"`（`tmuxPaneId` 也是 `"in-process"`）→ 同进程；
   - 有成员的 `backendType` 为 `"tmux"`（`tmuxPaneId` 形如 `"%6"`）或其他值 → 分窗格。
   - 这是 Claude Code 的内部文件，不是公开接口；读不到（例如 `-p` 模式下没有这个文件）或没有成员条目 → 进入第 2 步。只看本会话自己的这个目录。
2. **读用户级设置里的 `teammateMode`**：用 Read 工具读 `~/.claude/settings.json`。
   - 没有这一项或为 `in-process` → 同进程；
   - `tmux` 或 `iterm2` → 分窗格；
   - `auto` → 在 Bash 里运行 `printenv TMUX` 和 `printenv TERM_PROGRAM`（没有输出 = 没设置；以 1 退出不算命令失败）：`TMUX` 有输出，或 `TERM_PROGRAM` 为 `iTerm.app` 且 `command -v it2` 有结果 → 分窗格；否则 → 同进程。这些命令没能运行（被拒绝或报错）→ 按"不知道"处理。
3. **都判不出** → 按同进程的写法，并记下"没能确认"，结束消息里说明是推断。

**失败时**：任何一步出错都不影响团队，只影响结束消息里的这两处写法。

## Step E5: 判断登录方式：是不是 claude.ai 账号

**为什么**：远程控制只支持用 claude.ai 账号登录的 Claude Code。提前判断出来，结束消息就能直接告诉用户能不能开，用户不用自己对照账号类型。

**怎么做**：在 Bash 里运行

```bash
claude auth status 2>/dev/null | jq -r '[.authMethod // "", .subscriptionType // ""] | @tsv'
printenv ANTHROPIC_BASE_URL
```

（没登录时这条命令以 1 退出，但仍会输出 JSON，照常按 `authMethod` 判断。）按结果分三种，记下来供结束消息用：
- (a) `authMethod` 为 `claude.ai`，**且** `subscriptionType` 非空（例如 `max`）→ **claude.ai 账号登录**，记下 `subscriptionType` 的原样取值；
- (b) **不是 claude.ai 账号登录**，远程控制用不了。两种情形，记下是哪一种：
  - (b1) `authMethod` 是 `claude.ai` 以外的值：`api_key`、`api_key_helper`、`third_party`、`oauth_token`、`none`（没登录）等；
  - (b2) `ANTHROPIC_BASE_URL` 非空，且指向的不是 `api.anthropic.com`：即使 `authMethod` 是 `claude.ai`，远程控制也用不了。
- (c) **不知道**：命令失败、没有输出或解析不出（例如没有 jq）；或第二条命令没能运行（被拒绝或报错；它只是没有输出、以 1 退出，说明这个变量没设置，不算没能运行）；或 `authMethod` 是 `claude.ai` 但 `subscriptionType` 为空（较老的版本会把用 API 计费的 Console 登录也报成 `claude.ai`，这时分不清）。

先看 (b2)，再看 (a)、(b1)、(c)。这条命令只报告登录方式，不读凭据文件、不打印令牌；但它的输出里有邮箱和组织名，只用上面取出的两个字段，**不要**把原始输出写进任何消息。(c) 不算"未能检查的项"，结束消息里有它自己的写法，不要写进"有一项没能检查"。

**失败时**：任何出错都按 (c) 处理，不影响团队。

**结束前**（做完 Step E4、E5 之后）：
1. 用 TaskStop 停掉还没结束的后台计时（用记下的编号）；
2. 删除未完成标记（`rm -f <lead 工位>/.quickstart_incomplete`）；
3. 发结束消息（Step F）。
