## Plain vocabulary

- Use plain, precise, everyday words. Never coin metaphorical names for things. If a concept needs a name, use a plain descriptive one and define it where it first appears.
- Test: would a professional reader from outside this project understand the word at first sight? If not, replace it.
- Avoid abbreviations. If you must use some, put a short table of them at the top of your reply.
- Words the user has rejected (the lead, or a flat agent, adds one each time the user rejects a word; teammates send additions to their lead). Below is a starter list that ships with the framework; every entry is a word or phrase users rejected in real use. Add new ones as your users reject them, and delete any that do not apply to your project:
  - Phrases banned outright: "the swap of the two axes"; "the one-step sink jump"; "five vertical blocks + two cross-cuts".
  - Ordinary words banned only in the stated use:
    - "leg" for a branch of an experiment or a plan. Write "branch", "this set of runs", "control group".
    - "ruler" for a measuring standard. Write "metric" or "criterion".
    - "bought" / "buys us" meaning "obtained", as in "this design bought us equal compute and equal parameters". Write "obtained … at equal compute and parameter count".
    - "fingerprint" as a metaphor. It stays allowed as the precise technical term, for example a file's fingerprint (its hash).
